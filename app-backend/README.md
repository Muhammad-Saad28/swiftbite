# Swiftbite Backend & Flutter Integration Guide

This directory (`app-backend/`) contains all the necessary documentation, configuration, and data models to build the future Flutter mobile application using the existing Swiftbite infrastructure.

## 1. Existing Website Stack
- **Framework:** Next.js (App Router)
- **UI:** React, Tailwind CSS, Framer Motion
- **Language:** TypeScript
- **Package Manager:** npm

## 2. Existing Backend
The backend is completely serverless and powered by **Supabase**. 
- There are no custom Node.js/Next.js API routes used for core logic; the website interacts directly with the Supabase PostgreSQL database using the `@supabase/supabase-js` client.

## 3. Existing Database
- **Database:** PostgreSQL (managed via Supabase).
- **Core Entities:** `users`, `tables`, `categories`, `menu_items`, `orders`, `order_items`, `inventory`, `website_products`.
- **Security:** Protected via Row Level Security (RLS) policies.
- For a complete breakdown, see [DATABASE.md](./DATABASE.md).

## 4. Authentication
- Currently, the Supabase schema defines a `users` table with roles (admin, waiter, kitchen).
- See [AUTH.md](./AUTH.md) for details on how Flutter should authenticate.

## 5. API Endpoints
Since the backend relies on Supabase, the "API Endpoints" are standard RESTful endpoints automatically generated by Supabase PostgREST. See [API.md](./API.md).

## 6. Product/Menu Data
- The web app has hardcoded menu items in some files, but the database has full tables (`categories`, `menu_items`, `website_products`). The Flutter app should *exclusively* use the database to fetch these items dynamically to ensure a single source of truth.

## 7. Cart
- Handled via local state (React Context) in the web app. In Flutter, you will need a local state management solution (e.g., Provider, Riverpod, or Bloc) to store cart items before placing an order.

## 8. Favorites
- Currently, favorites/wishlist logic in the web app is likely local storage. If cloud syncing is required for Flutter, a new `favorites` table linking `user_id` to `menu_item_id` should be created in Supabase.

## 9. Orders
- Created in the `orders` and `order_items` tables.
- Subtotal, taxes, and inventory deductions are handled *automatically* via PostgreSQL Triggers in the existing database.

## 10. Payments
- Currently defined as `payment_method_enum` ('cash', 'card', 'qr_online', 'split') in the schema. Payment processing logic (like Stripe) is not present in the backend.

## 11. Assets
- The web app uses standard images (e.g., `/images/zinger.png`, `/images/beef-burger.png`). Reusable assets have been identified.

## 12. Environment Variables
- See [ENVIRONMENT.md](./ENVIRONMENT.md).

## 13. Flutter Integration
- Flutter should use the `supabase_flutter` package to connect directly to the existing Supabase project.

## 14. Recommended Flutter Architecture
- **State Management:** Riverpod or Bloc.
- **Backend Service:** `supabase_flutter`.
- **Data Models:** Use the provided Dart models in `models/flutter/`.

## 15. Known Limitations
- The website frontend has some hardcoded product data; Flutter should strictly read from the Supabase tables (`menu_items`, `categories`).
- Actual payment gateway integrations are missing on the backend.

## 16. Things NOT to copy from the website
- Do not copy Next.js UI components.
- Do not copy hardcoded menu data arrays.
- Do not copy the local React Context Cart implementation.
